# TaQ: F3 a F12 Implementation Plan

> **For agentic workers:** execute phases in order against `docs/roadmap/plan-implementacion-motor.md`; verification and tests are consolidated in the final task per the owner's instruction.

**Goal:** Move TaQ from the F2 delivery foundation to a defensible, multi-tenant pilot engine with configurable resumable sources, contextualized findings, human-approved actions, governed feedback, an authenticated API, production controls, and a release evidence pack.

**Architecture:** Keep Redpanda as the durable event log, PostgreSQL as the transactional control-plane/state store, and ClickHouse as the event/evidence projection. Build versioned domain contracts and deterministic rules before adding ML. Every external effect remains behind an approval and idempotent outbox. Deploy only after security/privacy and recovery controls are in place.

**Tech Stack:** Existing Rust/Tokio workspace, Redpanda/Kafka, ClickHouse, PostgreSQL, OpenTelemetry/Prometheus/Grafana, Docker Compose for local development and CI, HTTP JSON/OpenAPI, CLI.

**Spec:** `docs/roadmap/plan-implementacion-motor.md`; existing event, source, delivery, and observability contracts in `docs/adr/`.

## Global Constraints

- The product vertical is defensive OSINT for watched brands, domains, and organizations.
- One pilot operator administers policy; data and API records are tenant-isolated from the first persisted domain schema.
- Use public sources only, comply with published terms/rate limits, and do not treat public availability as permission for every use.
- Keep delivery at-least-once and consumers idempotent; retain event identity and provenance.
- Findings start with deterministic, versioned rules; ML does not enter the decision path in this plan.
- External actions require a human approval, support a kill switch, and use a durable idempotent outbox.
- Keep source, finding, action, feedback, and rule versions explicit and replayable.
- No production credential, private data, or external side effect is introduced by local/CI implementation.
- As requested, defer adding/running the project test suite and full validation until Task 10; do not claim behavior is validated before then.

## Review Focus

- Cursor checkpoint must be committed only after Kafka acknowledges the event; restart may duplicate but must not skip.
- Conditional RSS responses and inclusive Jetstream cursors must not advance state ahead of published events.
- A tenant may never read or mutate another tenant's watchlists, findings, actions, or feedback.
- An unapproved, expired, replayed, or revoked action must not execute externally.
- Candidate rule promotion must fail closed when holdout, provenance, or guardrail evidence is absent.

### Task 1: F3 source configuration and durable cursors

**Files:** source connectors; `taq-ingest` delivery contract; new Postgres state crate/migration; `taq-ingestd` configuration; `.env.example`; source-terms operations note; ADR.

Implement validated endpoint, polling, request/connect timeout, User-Agent, rate limit, queue capacity, and retry settings. Add conditional RSS requests (`ETag`, `Last-Modified`) and cursor resume for Wikimedia SSE and Bluesky Jetstream. Store opaque source checkpoints in PostgreSQL. Checkpoints advance only after the corresponding event publication ACK; inclusive replay is deduplicated through event identity.

### Task 2: F4 route-real E2E and readiness

Add deterministic local HTTP/SSE/WebSocket fixtures; exercise `taq-ingestd → Redpanda → ClickHouse`, typed source errors, lag/readiness, and bounded source metrics. Make CI distinguish connector-path E2E from direct loadgen validation. Record baseline hardware and measured throughput/latency without setting claims.

### Task 3: F5 tenant-scoped watchlists and context

Add versioned entities, aliases, domains and relationships in PostgreSQL; normalize IDNA domains; exact/normalized resolution first; bounded async enrichment and cache; versioned contextualized event projection with replay by context version. Choose tenant isolation before schema creation and preserve provenance.

### Task 4: F6 deterministic findings

Add versioned rules and deterministic evaluation. Store `Finding` with severity, score, tenant, rule/version, evidence event IDs/URLs/hashes, explanation, lifecycle status and idempotency key. Add thresholding, grouping and suppression; prepare a reproducible gold-set evaluation format.

### Task 5: F7 approval workflow and outbox

Add versioned signal-to-action policies, pending/approved/rejected/expired states, role-checked approvals, transactional outbox, retry/reconciliation, idempotency keys, audit trail, shadow mode and kill switch. No connector can perform an external effect without an approved outbox item.

### Task 6: F8 governed feedback

Persist attributed feedback against immutable finding/rule/dataset versions. Build candidate → offline gold/temporal-holdout evaluation → human promotion → shadow/canary → rollback. Add guardrails, rejection evidence, sampled non-alert events for recall, and drift reporting. Never auto-promote.

### Task 7: F9 authenticated API and CLI

Expose tenant-scoped list, findings/evidence, action approval, feedback, and webhook endpoints with OpenAPI. Store API-key hashes only; enforce scopes, RBAC, quotas, rate limits, pagination/versioning/idempotency and negative tenant-isolation checks. CLI calls the same API surface.

### Task 8: F10 privacy and security controls

Classify/minimize data; implement retention and deletion propagation across event log, ClickHouse, Postgres, caches, backups and exports; externalize secrets; least-privilege credentials/network; TLS/encryption configuration; dependency/secret scan and SBOM; threat model and legal-terms evidence. Keep unresolved legal decisions as release blockers, not assumed approvals.

### Task 9: F11 production operations and F12 release qualification

Add non-development deployment configuration, immutable artifacts, staged migration/rollback, backups and restore rehearsal, health/readiness, SLI dashboards/alerts/runbooks and failure drills. Generate a release evidence pack for E2E, sustained-load benchmarks, source terms, gold-set precision/recall, security/privacy, restore/rollback and explicit G2/G3 Go/No-Go; make all unmeasured claims unavailable by default.

### Task 10: Consolidated final validation

Only after Tasks 1–9 are implemented, add/finish the tests requested by the owner and run full formatting, lint, workspace tests, dependency/secret checks, Compose validation, and Docker E2E. Run end-to-end scenarios with ephemeral infrastructure; archive evidence and update roadmap/context with measured results only. Any unavailable Docker/legal/production credential prerequisite remains explicitly unverified and cannot be marked as a launch gate passed.
